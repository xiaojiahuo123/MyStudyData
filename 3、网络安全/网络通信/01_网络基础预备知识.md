## 1. 为什么要分层：OSI 与 TCP/IP

网络复杂到没法一口气设计完，所以被切成一层一层的。每一层只管自己的事，向上提供服务，向下调用服务。

| 层（TCP/IP 模型） | 对应 OSI 层 | 这层管什么 | 典型设备 | 数据单位叫法 |
|---|---|---|---|---|
| 应用层 | 应用/表示/会话 | 具体的程序协议 | 电脑、服务器 | 报文 / Data |
| 传输层 | 传输层 | 端到端的可靠/不可靠传输，**端口号** | 防火墙（四层） | 段（Segment）/ 数据报 |
| 网际层（IP 层） | 网络层 | **IP 地址、跨网段寻址、路由** | **路由器**、三层交换机 | 包（Packet） |
| 网络接口层 | 数据链路层 | **MAC 地址、同一网段内寻址、成帧** | 交换机、网卡 | 帧（Frame） |
| （物理层） | 物理层 | 电信号、光信号、网线接口 | 网线、光模块、Hub | 比特（Bit） |

**这份配置里的东西几乎全在"网际层 + 网络接口层"**——路由器主要干的就是"看 IP 地址决定从哪个口扔出去"。

### 封装：数据一路往下穿衣服

你发一条微信，数据在发送端是这样被打包的：

```
应用数据  "hello"
  ↓ 加 TCP 头（源端口 5000，目的端口 443，序号...）
TCP 段
  ↓ 加 IP 头（源 IP 192.20.27.100，目的 IP 173.20.1.50）
IP 包
  ↓ 加以太网头（源 MAC aa:bb:cc...，目的 MAC dd:ee:ff...）+ 帧尾校验
以太网帧
  ↓ 变成电信号
网线上的比特流
```

**关键洞察（这是理解全篇的钥匙）**：

- 在**整个跨网段旅程中，IP 头里的源 IP 和目的 IP 基本不变**（NAT 除外）。
- 但**MAC 地址每经过一个路由器就会重写一次**——因为 MAC 只在"这一段链路"上有意义。

```
[PC] ──帧1──> [路由器R1] ──帧2──> [路由器R2] ──帧3──> [服务器]

帧1: 目的MAC = R1的MAC     IP: 源=PC   目的=服务器
帧2: 目的MAC = R2的MAC     IP: 源=PC   目的=服务器   ← IP 没变，MAC 换了
帧3: 目的MAC = 服务器的MAC  IP: 源=PC   目的=服务器
```

## 2. MAC 地址与 IP 地址：两套编号系统

| | MAC 地址 | IP 地址 |
|---|---|---|
| 长度 | 48 bit，写成 `84:46:FE:3D:54:53` | IPv4 32 bit，写成 `192.20.27.18` |
| 谁分配 | 前 24 位（OUI）由 IEEE 分配给厂商，后 24 位厂商自己编 | 网络管理员分配，**可以改** |
| 能否修改 | **能。** 出厂值烧在硬件里，但操作系统/驱动可以覆盖它 | 能，本来就是配出来的 |
| 唯一性 | 设计上期望全球唯一，**实际上可能被修改、伪造或重复** | 在网络内必须唯一（重复就是 IP 冲突） |
| 作用范围 | 只在**同一段链路**有效 | **全网**有效，可跨网段 |
| 是否分层 | 扁平，地址里不含位置信息 | **有层级**，地址里含"网段"信息（靠掩码） |
| 类比 | 车牌（理论上唯一，但可以套牌） | 邮寄地址（含省市区，能路由） |

> ⚠️ **易错提示：MAC 地址不是"出厂烧死、全球唯一、不可更改"**
>
> 这是初学者最常见的错误认知，而且**在安全方向尤其要命**——正因为 MAC 可改，才有一整类二层攻击存在：
>
> | 场景 | 说明 |
> |---|---|
> | **手动修改** | Linux：`ip link set eth0 address 02:11:22:33:44:55`；Windows：网卡属性 → 高级 → "网络地址 / Network Address" |
> | **虚拟化环境** | VMware / Hyper-V / KVM / Docker 的虚拟网卡 MAC 由软件生成，**重复非常常见**（尤其是虚机克隆） |
> | **MAC 欺骗（Spoofing）** | 攻击者把自己的 MAC 改成别人的，绕过 MAC 地址过滤、冒充网关 |
> | **MAC 泛洪（CAM Overflow）** | 攻击者伪造海量不同源 MAC 刷爆交换机 MAC 表，交换机被迫广播，攻击者就能嗅到别人的流量 |
>
> 所以：**任何基于 MAC 的认证或过滤都是弱的**，只能防君子，不能当作真正的安全边界。

**为什么需要两套？** 因为历史原因：先有以太网（用 MAC），后有 IP。IP 的优势是**地址有结构**，可以聚合——路由器只需要记"去 192.20.27.0/24 走这个口"，而不用记 254 台机器各自的 MAC。如果全用 MAC，全球路由表会有几十亿条，直接爆炸。

> 配置里 `drop illegal-mac alarm` 就是跟 MAC 有关的：发现**源 MAC 不合法**的帧（比如源 MAC 是广播地址、组播地址、全 0）就告警丢弃。注意它只拦"格式上根本不可能合法"的帧（通常是攻击工具或故障网卡产生的），**拦不住格式合法但内容伪造的 MAC 欺骗**。

## 3. IP 地址到底怎么读：子网掩码与网段

### 3.1 点分十进制与二进制

IP 地址 `192.20.27.18` 本质是 32 个 bit：

```
192  .   20  .   27  .   18
11000000 00010100 00011011 00010010
```

### 3.2 掩码的作用：划一条线

掩码 `255.255.255.0` 二进制是 24 个 1 + 8 个 0：

```
11111111 11111111 11111111 00000000
└──────── 网络位 ────────┘ └ 主机位 ┘
```

- **网络位**：标识"这是哪个网段"，同一网段的机器网络位完全相同
- **主机位**：标识"网段里的哪台机器"

所以 `255.255.255.0` = `/24`（前 24 位是网络位），这就是 CIDR 斜杠记法的来源。

### 3.3 算出网段

把 IP 和掩码做**按位与（AND）**：

```
IP:    192.20.27.18  = 11000000.00010100.00011011.00010010
掩码:  255.255.255.0 = 11111111.11111111.11111111.00000000
AND ─────────────────────────────────────────────────────
网段:  192.20.27.0   = 11000000.00010100.00011011.00000000
```

**广播地址**：主机位全 1 → `192.20.27.255`（发给这个地址 = 发给网段内所有人）

### 3.4 常见掩码对照表

| CIDR | 掩码 | 总地址数 | 可用主机数 | 典型用途 |
|---|---|---|---|---|
| /32 | 255.255.255.255 | 1 | 1 | **Loopback 回环口**（配置里的 10.10.30.53） |
| /30 | 255.255.255.252 | 4 | **2** | **两台路由器点对点互联**（配置里 10.10.1.53、192.80.106.1） |
| /24 | 255.255.255.0 | 256 | 254 | **普通局域网**（配置里的 LAN A、LAN B） |
| /16 | 255.255.0.0 | 65536 | 65534 | 大型园区网 |

**为什么要减 2？** 每个网段有 2 个地址不能给主机用：
- 网段地址（主机位全 0）：`192.20.27.0`
- 广播地址（主机位全 1）：`192.20.27.255`

### 3.5 /30 为什么是"两台路由器互联"的标准

`192.80.106.1/30`：
```
网段:   192.80.106.0   ← 不能用
可用1:  192.80.106.1   ← 本端（xingguo_r1 的 G0/0/11）
可用2:  192.80.106.2   ← 对端（宁都方向路由器）
广播:   192.80.106.3   ← 不能用
```

广域网专线按带宽收费、IP 地址稀缺，两个路由器之间只需要 2 个地址，用 /30 最省。配置里 `10.10.1.53/30` 同理（对端是 .54）。

### 3.6 私有地址 vs 公网地址

RFC 1918 规定三段地址**不会出现在公网上**，谁都能在内网随便用：

| 段 | 范围 |
|---|---|
| 10.0.0.0/8 | 10.0.0.0 ~ 10.255.255.255 |
| 172.16.0.0/12 | 172.16.0.0 ~ 172.31.255.255 |
| 192.168.0.0/16 | 192.168.0.0 ~ 192.168.255.255 |

**注意这份配置里的地址**：`192.20.x.x`、`192.80.x.x`、`173.20.x.x`、`10.10.x.x` —— 其中只有 `10.10.x.x` 落在 RFC 1918 私有段内，`192.20.x.x`、`192.80.x.x`、`173.20.x.x` **都不在私有段里**。

> ⚠️ **易错提示：不能从"不是私有地址"推断出"对方合法拥有公网地址"**
>
> 看到 `192.20.x.x` 这种地址，只能得出一个结论：**它不是 RFC 1918 私有地址**。仅此而已。
> 想推断它的归属，可能性至少有三种，配置本身无法区分：
>
> | 可能性 | 说明 |
> |---|---|
> | (a) 合法申请 | 该组织确实向 APNIC/CNNIC 申请了这段公网地址空间 |
> | (b) **在隔离专网里借用** | 网络与互联网物理隔离，于是"借用"了别人名下的号码段。老专网里极其常见——建网时没申请，改址成本又太高，就这么一直用着 |
> | (c) 纯粹的内部编号 | 规划者压根没考虑公网/私网的区分，随手挑的 |
>
> **这也正好解释了配置里为什么有那么多 `filter-policy`**：不管这些地址归谁，只要这个专网某天要和外部（哪怕是互联网）互通，这些"借用"的地址就是冲突源和泄漏源。严格过滤路由，既是防路由劫持，也是防止把内部编号泄漏出去。
>
> 排障时的实际影响：如果你接入另一个专网或互联网，发现 `192.20.x.x` 已经指向别的地方，你自己的路由就会冲突——这是专网互联时最头疼的问题之一。

## 4. 反掩码（通配符）：ACL 里的 0.0.0.255 是什么

配置里到处是这种：

```
acl number 2002
 rule 5 permit source 192.20.27.0 0.0.0.255
```

这里的 `0.0.0.255` **不是**子网掩码，是**通配符掩码（wildcard mask）**，逻辑**完全相反**：

| | 子网掩码 | 通配符掩码 |
|---|---|---|
| bit = 1 | 这个 bit 属于**网络位**，必须匹配 | 这个 bit **不在乎**（任意） |
| bit = 0 | 这个 bit 属于**主机位**，任意 | 这个 bit **必须精确匹配** |

```
0.0.0.255 = 00000000.00000000.00000000.11111111
             └─ 必须匹配 ─┘  └─ 不在乎 ─┘
```

所以 `192.20.27.0 0.0.0.255` 意思是：**前 24 位必须等于 192.20.27，最后 8 位随意** = 整个 `192.20.27.0/24` 网段。

### 快速换算

```
/24 掩码 255.255.255.0   →  通配符 0.0.0.255
/30 掩码 255.255.255.252 →  通配符 0.0.0.3
/32 掩码 255.255.255.255 →  通配符 0.0.0.0     （精确匹配单个地址）
```

心算口诀：`通配符 = 255.255.255.255 - 子网掩码`

```
255.255.255.255
- 255.255.255.0
───────────────
   0.  0.  0.255   ✓
```

### 配置里的 `0.0.0.0`

OSPF 里出现 `network 10.10.1.53 0.0.0.0` —— 通配符全 0 表示**精确匹配这一个 IP**，即"只把这个接口地址所在的接口宣告进 OSPF"。这是最精确的写法（OSPF 的 network 命令后面跟的也是通配符，不是掩码）。

## 5. 网关：数据包出门的第一跳

假设 PC 是 `192.20.27.100/24`，它要访问 `173.20.1.50`。

PC 的判断逻辑（**这段一定要理解，很多人卡在这里**）：

```
1. 拿目的 IP 和自己的掩码做 AND
   173.20.1.50 AND 255.255.255.0 = 173.20.1.0
2. 我的网段是 192.20.27.0
3. 173.20.1.0 ≠ 192.20.27.0  →  "不是同一网段！"
4. 同网段: 直接 ARP 问目的 IP 的 MAC，封装帧发出去
   不同网段: 发给"网关"，由网关代为转发
```

**网关 = 本网段的出口路由器接口的 IP。**

在这份配置里，PC 的网关配的是 `192.20.27.20` —— 注意，这个 IP **在任何物理接口上都找不到**！它是 **VRRP 虚拟 IP**（见第 11 节）。

```
interface GigabitEthernet0/0/2
 ip address 192.20.27.18 255.255.255.0      ← 物理接口真实 IP
 vrrp vrid 10 virtual-ip 192.20.27.20       ← 虚拟网关 IP（PC 用这个）
```

两台路由器"合演"成一个网关，PC 完全不知道背后有几台路由器。

## 6. 交换机 vs 路由器：二层与三层

| | 交换机（二层） | 路由器（三层） |
|---|---|---|
| 看什么地址 | MAC 地址 | IP 地址 |
| 核心表项 | MAC 地址表（端口 ↔ MAC） | 路由表（网段 ↔ 下一跳/出接口） |
| 能干什么 | 同一网段内转发 | 跨网段转发 |
| 隔离广播域 | 不能（所有口一个广播域） | **能**（每个接口一个广播域） |
| 典型配置 | VLAN、Trunk、MAC 表 | IP 地址、路由协议、ACL、NAT |

### VLAN：把一台交换机切成多台

VLAN（虚拟局域网）让一台物理交换机表现得像多台独立交换机。不同 VLAN 之间默认不通，必须经过三层设备（路由器或三层交换机）。

> **这份配置里 VLAN 的情况**：配置中没有任何 VLAN、Trunk、Access 相关命令。真正在用的 5 个接口（G0/0/2、3、4、10、11）都配了 IP 地址、都在跑三层功能，说明这台设备**纯粹当路由器用**，VLAN 划分交给下联的接入层交换机。

> ⚠️ **易错提示：不要说"所有口都是三层路由口"**
>
> 这份配置里**只有 5 个接口明确执行了 `undo portswitch`**：GigabitEthernet0/0/2、3、4、10、11。
> 其余接口（G0/0/0、1、5~9、12、13）在导出配置中只有一行 `interface GigabitEthernet0/0/X`，
> 后面什么都没有——**这说明它们没有非默认配置，但导出文本本身不告诉你默认值是什么。**
>
> 华为设备的接口默认模式取决于**具体型号和接口类型**：有的 AR 型号以太网口默认就是三层路由口，
> 有的（尤其带交换模块的接口）默认是二层口，也有的可以通过 `portswitch` 在两者间切换。
> 单凭一份 `display current-configuration` **无法判定**未配置接口的模式。
>
> 严谨的说法应该是：
> - **确定是三层口**：G0/0/2、3、4、10、11（显式 `undo portswitch` + 配了 IP）
> - **模式未知**：其余接口，需要 `display interface GigabitEthernet0/0/X` 或看型号文档才能确定
> - **但都不参与三层转发**：因为它们没有 IP 地址
>
> 顺带一个观察：既然配置者要给这 5 个口写 `undo portswitch`，说明**这些口在他这台设备上的默认状态不是三层**，
> 否则命令是多余的。这也印证了不能想当然地推断其他口。

### `undo portswitch`：把二层口改成三层口

华为很多路由器的以太网口默认是**二层模式**（像交换机口一样），要配 IP 必须先切成三层模式：

```
interface GigabitEthernet0/0/2
 undo portswitch                    ← 切成三层路由口
 ip address 192.20.27.18 255.255.255.0   ← 现在才能配 IP
```

这是华为 VRP 的特色命令，**不看这行会以为接口没法配 IP**。

### Loopback 回环接口

```
interface LoopBack0
 ip address 10.10.30.53 255.255.255.255
```

- 这是**虚拟接口**，永远 up，不依赖任何物理线路
- 用作路由器的"身份证号"（Router-ID）
- 建 iBGP 邻居时用它当源地址，这样任何一条物理链路断了，邻居都不会跟着断（因为还有别的路能到 Loopback）
- /32 掩码，一个地址就够

### NULL0 接口

逻辑上的"垃圾桶"，指向它的流量直接丢弃。常用于做**黑洞路由**防环路（配置里只是默认存在，没被使用）。

## 7. 路由表与"下一跳"：路由器怎么知道往哪发

路由器收到一个 IP 包，做的事非常机械：

```
1. 查目的 IP
2. 在路由表里找"能匹配上的最精确的那条"（最长前缀匹配）
3. 按那条指示，从某个接口发给某个下一跳
4. 找不到 → 丢弃（然后可能回一个 ICMP 不可达）
```

### 最长前缀匹配（Longest Prefix Match）

假设路由表里有：

| 目的网段 | 下一跳 |
|---|---|
| 0.0.0.0/0（默认路由） | 192.80.1.1 |
| 173.20.0.0/16 | 10.10.1.54 |
| 173.20.1.0/24 | 192.80.1.1 |

来了一个目的 `173.20.1.50` 的包，三条都能匹配上，选**掩码最长的**：`173.20.1.0/24`。

**这条规则是 BGP 精细控制的基础**——想让某部分流量走特殊路径，就通告一条更精确的路由。

![](.\images\路由器\Snipaste_2026-09-07_21-02-24.png)

### 一条路由长什么样

```
Destination/Mask    Proto   Pre  Cost  NextHop       Interface
173.20.1.0/24       BGP     255  0     192.80.1.1    GigabitEthernet0/0/10
192.20.27.0/24      Direct  0    0     192.20.27.18  GigabitEthernet0/0/2
10.10.30.54/32      OSPF    10   2     10.10.1.54    GigabitEthernet0/0/4
```

| 字段 | 含义 |
|---|---|
| Destination/Mask | 目的网段 + 掩码 |
| Proto | 路由来源（Direct 直连 / Static 静态 / OSPF / BGP） |
| **Pre（优先级）** | 不同协议之间比大小，**越小越优先** |
| Cost | 同一协议内部比大小，**越小越优先** |
| NextHop | 下一个要交给谁 |
| Interface | 从自己的哪个口发出去 |

### 协议优先级（华为默认）

| 路由协议 | 优先级 |
|---|---|
| 直连 Direct | **0**（最高） |
| OSPF 内部 | 10 |
| 静态 Static | 60 |
| RIP | 100 |
| **IBGP** | **255** |
| **EBGP** | **255** |

**注意 BGP 是 255**（最低优先级）。这意味着：如果同一条路由 OSPF 和 BGP 都学到了，一定选 OSPF。设计时就靠这个来控制主备。

> 优先级值域说明：华为把 IBGP 和 EBGP 都设为 255；Cisco 是 eBGP 20 / iBGP 200。比较永远只在**不同协议之间**进行，同一协议内部比 Cost/属性。

## 8. 路由从哪来：直连、静态、动态路由协议

### 三种来源

| 类型 | 怎么产生 | 优点 | 缺点 |
|---|---|---|---|
| **直连路由** | 接口配了 IP 且 up，自动生成 | 零配置 | 只能到"自己接着的"网段 |
| **静态路由** | 管理员手敲 `ip route-static` | 可控、省资源 | 拓扑一变就要改，不会自愈 |
| **动态路由** | 路由器之间跑协议互相告知 | **自动收敛、能绕开故障** | 复杂、占资源、配错会出大事 |

这份配置里跑的是 **OSPF** 和 **BGP** 两个动态协议。

### 收敛（Convergence）

网络拓扑变了（比如一条线断了），所有路由器重新算路由、更新路由表的这个过程叫**收敛**，耗时叫**收敛时间**。

配置里这几行就是在**把收敛时间往死里压**：

```
bgp 2014
 timer keepalive 5 hold 15              ← 默认 60/180，改成 5/15
 peer 10.10.30.54 route-update-interval 5   ← 默认 15s，改 5s
 peer 192.80.1.1 route-update-interval 5    ← 默认 30s，改 5s
```

工业控制网络（这份配置看起来是电力/交通专网）对中断时间极敏感，宁可多耗 CPU 也要快。

## 9. IGP 与 EGP：OSPF 和 BGP 的分工

这是**全篇最重要的概念**，很多人学不会路由就是因为没搞清它俩的区别。

| | **IGP**（内部网关协议） | **EGP**（外部网关协议） |
|---|---|---|
| 用在哪 | **一个组织内部** | **组织与组织之间** |
| 代表 | OSPF、IS-IS、RIP、EIGRP | **BGP**（事实上唯一） |
| 目标 | 找**最快**的路 | 找**策略允许**的路 |
| 度量 | Cost（带宽算出来的） | 一大堆属性（AS_PATH、Local_Pref、MED...） |
| 规模 | 几百到几千条路由 | **几十万条**（互联网全表） |
| 速度 | 秒级收敛 | 慢，故意的（稳） |
| 信任度 | 内部设备，可信 | **外部，不可信，必须过滤** |

### 一个比喻

- **IGP（OSPF）** 像公司内部的部门电话表：追求"打通最快"，谁都能互相问。
- **BGP** 像公司和外部合作伙伴的商务协议：追求"我只告诉你该告诉你的，我只接受我想接受的"，速度和最优是次要的，**可控**才是第一位的。

![](.\images\路由器\Snipaste_2026-09-07_21-16-38.png)

### 这份配置的经典分工

```
OSPF：只跑内部基础设施（10.10.1.52/30 互联 + 10.10.30.53/32 Loopback）
      → 目的：让两台路由器之间"互相找得到"，支撑 iBGP

BGP：  负责业务网段（192.20.27.0/24、192.20.28.0/24）
      → 目的：和上级（AS 1001）、备份链路（AS 3002）交换业务路由
      → 顺便做严格的进出过滤（filter-policy）
```

**为什么不让 OSPF 也学业务网段？** 因为业务路由要用 BGP 的属性（Local_Preference 等）做精细控制，而且要用 ACL 严格限制"哪些能说出去、哪些能听进来"。OSPF 做不到这种级别的策略控制。

## 10. AS 自治系统：BGP 里的"国家"概念

**AS（Autonomous System，自治系统）** = 一个独立管理域，用 **AS 号**标识。

```
【16 位 AS 号】—— 传统，现已耗尽
  1 - 64511          公网 AS（需向 IANA 及地区注册机构申请）
  64512 - 65534      私有 AS（内部随便用，类似私有 IP）
  65535              保留，不使用
  23456              AS_TRANS，特殊：用来跟 32 位 AS 号做转换

【32 位 AS 号】—— RFC 6793，现在的主流
  65536 - 4294967295（约 43 亿个）
  其中 4200000000 - 4294967295 是私有 32 位 AS（RFC 6996）
  两种写法：
    asplain：65536        （华为默认，纯数字）
    asdot ：1.0           （思科常见，"点分"形式，1.0 = 65536）
```

配置里的 AS 号：

| AS 号 | 谁 | 判断依据 |
|---|---|---|
| **2014** | 兴国本地（本地 AS） | `bgp 2014` 是本机启动的 |
| **1001** | 南昌主站 / 上级 | `peer 192.80.1.1 as-number 1001` |
| **3002** | 宁都方向 | `peer 192.80.106.2 as-number 3002` |

![](.\images\路由器\Snipaste_2026-09-08_08-59-08.png)

> ⚠️ **易错提示：AS 号范围不要死记"1-64511 公网 / 64512-65535 私有"**
>
> 这是**过时的 16 位简化说法**，三条都要修正：
> 1. **65535 不是私有**，它是保留号；私有段是 **64512-65534**
> 2. **公网段里有保留号**：0、23456、64496-64511（文档示例用）等有特殊用途，不是随便能申请的
> 3. **还有 32 位 AS 号**：现在新申请的几乎都是 32 位的，总数约 43 亿，早就不止 65535 了
>
> 另外，和 IP 地址那条呼应：**看到 AS 号在公网段内，也不能推断对方合法申请了它。**
> 隔离专网里随便挑个 AS 号（比如挑年份 2014）是很常见的做法。

### eBGP 与 iBGP

| | **eBGP** | **iBGP** |
|---|---|---|
| 全称 | External BGP | Internal BGP |
| 建在哪 | **不同 AS 之间** | **同一个 AS 内部** |
| 判断方法 | peer 的 AS 号 ≠ 自己的 | peer 的 AS 号 = 自己的 |
| 本配置 | 192.80.1.1（AS 1001）、192.80.106.2（AS 3002） | 10.10.30.54（AS 2014，就是 r2） |
| 下一跳行为 | 会改成自己 | **默认不改**（所以需要 `next-hop-local`） |
| 防环 | AS_PATH（看到自己的 AS 号就拒收） | **水平分割**（从 iBGP 学到的不再转发给其他 iBGP 邻居） |

### iBGP 水平分割 —— 为什么这个坑很重要

> 规则：路由器从 iBGP 邻居学到的路由，**不会**再通告给任何其他 iBGP 邻居。

目的：防环。副作用：**iBGP 邻居必须全互联（full mesh）**，或者用路由反射器（Route Reflector）/ 联盟（Confederation）。

这份配置只有两台路由器（r1 和 r2），两台之间全互联就够了，所以不需要反射器。

### 为什么 iBGP 要用 Loopback 建邻

```
peer 10.10.30.54 as-number 2014
peer 10.10.30.54 connect-interface LoopBack0
```

如果用物理接口 `10.10.1.53` 建邻，这条链路一断，BGP 邻居立刻 down。用 Loopback 建邻，则**只要还存在任意一条能到达对端 Loopback 的路径，BGP 邻居就还活着**。

**Loopback 是路由器的"人"，物理接口是它的"衣服"，人要找人，不要找衣服。**

> ⚠️ **易错提示：Loopback 建邻不是"永不断"，它的前提是"有多条冗余路径"**
>
> 上面那句"只要任意路径能通"有个**必须满足的前提**——网络里真的得有第二条路。
> **回到这份配置，很遗憾：没有。**
>
> ```
> ospf 1 router-id 10.10.30.53
>  area 0.0.0.0
>   network 10.10.1.53 0.0.0.0      ← 只有 G0/0/4 这一条互联链路
>   network 10.10.30.53 0.0.0.0     ← Loopback 自己
> ```
>
> OSPF 只宣告了一个互联网段。也就是说，r1 到 r2 的 Loopback（10.10.30.54）
> **只有 G0/0/4 这一条路可走**。那么：
>
> ```
> G0/0/4 中断
>   → OSPF 邻居 down
>   → 到 10.10.30.54 的路由消失
>   → iBGP 邻居 TCP 连接断开
>   → iBGP 照样 down
> ```
>
> **所以在这份具体配置里，用 Loopback 建邻并没有换来"抗链路故障"的能力。**
> 它带来的实际好处只剩两个：
> 1. **配置解耦**：接口 IP 改了（比如互联网段从 10.10.1.x 换成别的），BGP 的 peer 地址不用动
> 2. **Router-ID 稳定**：Loopback 地址不会因接口 down 而消失
>
> 想让 Loopback 建邻真正发挥作用，需要**至少两条物理上独立的路径都跑 OSPF**，
> 比如再加一条 r1-r2 的备份互联，或者让上行链路也能承载到对端 Loopback 的流量。
> 这是一个"配置模板抄对了，但没配套上让它生效的拓扑"的典型例子。

## 11. 冗余：为什么什么都得有两份

工业/专网的核心诉求：**不能断**。所以任何单点都要备份。

### 11.1 链路冗余：两条上行

```
链路 A：G0/0/10 → 192.80.1.1（AS 1001，南昌主站，192.80.1.0/24 以太网）
链路 B：G0/0/11 → 192.80.106.2（AS 3002，宁都 DDN 2M 专线）
```

`description To_NingDu-DDN-2M` —— DDN 是数字数据网（Digital Data Network），一种老式专线。`2M` 是带宽 2Mbps（E1 线路）。

> ⚠️ **易错提示：不要直接把链路 A 叫"主用"、链路 B 叫"备用"，这份配置没有这样保证**
>
> 从 description、带宽、网段形态看，**设计意图**确实是 A 主 B 备。但**意图 ≠ 配置保证的结果**。
> 逐个证据看这份配置实际做了什么：
>
> | 观察点 | 实际配置 | 说明 |
> |---|---|---|
> | 去往 173.20/173.21 网段 | lp01 只给**从南昌收到**的这两个网段打 Local_Pref 400 | 只覆盖了**两个特定网段**，不是"所有流量优先走南昌" |
> | 其他路由（如 192.20.102.0/24） | **没有任何策略干预** | 完全由默认 BGP 选路规则决定，可能走南昌也可能走宁都 |
> | 向宁都通告 | ACL 2004 = **只有 LAN A** | 宁都方向**看不到 LAN B**，所以它根本不是 LAN B 的备份 |
> | 宁都链路的 metric/属性 | 无 MED、无 AS_PATH 追加 | 没有做"让宁都变差"的显式设置 |
>
> **所以准确的说法是**：
> - 对于 `173.20.1.0/24` 和 `173.21.1.0/24`，配置**明确保证**了优先走南昌（Local_Pref 400）
> - 对于 LAN A，宁都方向**是一份不完整的备份**（只有 LAN A 被通告过去）
> - 对于 LAN B 和其他所有路由，**这份配置没有做出主备保证**
>
> 真正要确认主备关系，需要看 r2 的配置、以及实设备上 `display bgp routing-table` 的
> 实际选路结果。**从单个设备的配置文件推断全网行为，本身就是有风险的**——
> 这也是网络排障时必须四面取证的原因。

### 11.2 设备冗余：VRRP

**VRRP（Virtual Router Redundancy Protocol，虚拟路由器冗余协议）**：

```
        ┌─────────────┐
        │  虚拟网关    │
        │192.20.27.20 │  ← PC 的网关配这个
        └──────┬──────┘
          ╱            ╲
    ┌────────┐      ┌────────┐
    │  r1    │      │  r2    │
    │.18     │      │.19(推测)│
    │prio 120│◄────►│prio 100│
    │ MASTER │ 心跳 │ BACKUP │
    └────────┘      └────────┘
```

- 两台路由器组成一个"虚拟路由器"，共用一个虚拟 IP
- **优先级（priority）越大越优先**，默认 100
- 配置里 r1 是 **120** → r1 是 **Master**（干活），r2 是 Backup（待命）
- 它们之间发 VRRP 通告报文（默认 1 秒一次）；Backup 一段时间收不到就顶上
- PC 完全无感知，网关 IP 一直不变

```
interface GigabitEthernet0/0/2
 vrrp vrid 10 virtual-ip 192.20.27.20
 vrrp vrid 10 priority 120        ← 高于默认 100，所以是 Master
```

**VRRP 组号（vrid）**：一个接口可以属于多个 VRRP 组，组号用来区分。LAN A 用 vrid 10，LAN B 用 vrid 11。

> 高级用法：可以让 r1 在 vrid 10 是 Master，在 vrid 11 是 Backup，实现**负载分担**。这份配置里两个组都给了 120，说明 r1 是两个 VLAN 的主，全部流量走 r1，r2 纯备份。

### 11.3 冗余的代价：三个必须想清楚的问题

1. **脑裂（Split-Brain）**：心跳线断了但两台都没坏，都以为自己是 Master。→ 需要多条心跳路径 + 监控。
2. **主备切换后的回切**：修好后要不要自动切回来？（VRRP 默认开启抢占 preempt）
3. **非对称路由**：去的路走 r1，回的路走 r2，如果中间有防火墙/NAT 就会出问题。设计时要保证来回路径一致。

## 12. 三个平面：SSH、SNMP、NTP、AAA

理解设备的三个"平面"是网络安全的基本功。它们是**按流量的用途**划分的：

```
┌─────────────────────────────────────────────────────────┐
│  管理平面 Management Plane                               │
│  "人/网管系统 对 设备说话"                                 │
│  SSH / Telnet / HTTPS / SNMP / NTP / AAA / Syslog / FTP  │
├─────────────────────────────────────────────────────────┤
│  控制平面 Control Plane                                  │
│  "设备 对 设备说话"，用来计算和维护转发表                   │
│  OSPF / BGP / RIP / ARP / VRRP / STP / 路由表→FIB        │
├─────────────────────────────────────────────────────────┤
│  数据平面 Data Plane（转发平面）                           │
│  "路过的数据包"，设备按 FIB 无脑转发                       │
│  接口收发 / ACL 过滤 / NAT / QoS / 二层交换                │
└─────────────────────────────────────────────────────────┘
```

| 平面 | 流量属于谁 | 典型协议 | 被攻击的后果 |
|---|---|---|---|
| **管理** | **发给设备自己**的管理流量 | SSH、SNMP、NTP、AAA | **设备被控**（最常见） |
| **控制** | **发给设备自己**的协议报文 | OSPF、BGP、VRRP、ARP | 路由被篡改、流量被劫持 |
| **数据** | **穿过设备**的用户流量 | 各种业务流量 | 被窃听、被丢弃（DoS） |

> ⚠️ **易错提示：不要把"控制平面"和"管理平面"合并成一个**
>
> 两者虽然都是"发给设备自己的流量"，但性质完全不同：
> - **控制平面**是设备之间自动协商（路由协议自己跑，人不管）
> - **管理平面**是人或网管系统主动发起（SSH 登录、SNMP 查询）
>
> 混淆它们会导致**漏掉一整个攻击面**。三个平面各有各的打法：
>
> | 平面 | 典型攻击 | 防御手段 |
> |---|---|---|
> | 管理平面 | 弱口令、明文协议、越权 | 强密码、SSH/HTTPS、登录源 ACL、权限分级 |
> | 控制平面 | **伪造 OSPF LSA / BGP 路由注入**、ARP 欺骗、VRRP 抢占 | **路由协议认证**、BFD、ACL 保护协议端口 |
> | 数据平面 | DoS 洪泛、扫描、嗅探 | ACL、限速、加密（IPsec/MACsec） |
>
> **回到这份配置**：本书前面重点讲的是管理平面的问题（Telnet、弱密码、无登录源限制）。
> 但顺着这个三平面模型一对照，会发现**控制平面也有一个明显的空缺**：
>
> ```
> ospf 1                              ← 没有 authentication-mode
> bgp 2014                            ← 没有 peer X.X.X.X password
> ```
>
> **OSPF 和 BGP 都没配认证。** 意味着任何人只要能接入 `10.10.1.52/30` 这个网段
> （比如插根网线到那台交换机），就能和 r1 建立 OSPF 邻居、向它注入路由，
> 把全网流量引到自己机器上。**这是比弱密码更隐蔽的入侵路径**——因为它不需要任何账号。
>
> 正确做法：
> ```huawei
> ospf 1
>  area 0
>   authentication-mode md5 1 cipher <密码>
> bgp 2014
>  peer 10.10.30.54 password cipher <密码>
>  peer 192.80.1.1 password cipher <密码>
> ```
>
> 详见精读文档安全审计部分（已补充为第 13 项）。

**网络安全学习重点关注管理平面**——绝大多数真实世界的设备被控，都是从管理平面进来的，不是从数据平面。但**控制平面一旦被攻破，破坏范围更大**（能劫持全网流量），只是门槛更高。

| 协议 | 干什么 | 端口 | 这份配置的状态 |
|---|---|---|---|
| **Telnet** | 远程命令行 | 23 | ⚠️ **明文传输**，密码能被抓包看到。绝对不该用 |
| **SSH / Stelnet** | 加密的远程命令行 | 22 | ⚠️ 服务开了，但 **15 级账号 admin 的 service-type 里没有 ssh**（只有 telnet 和 http），所以这个最高权限账号**反而登不进来** |
| **HTTP** | 明文 Web 管理 | 80 | ⚠️ 不安全，但受下面那条限制，**实际不可达** |
| **HTTPS** | 加密 Web 管理 | 443 | ⚠️ "开了"≠"安全"，见下方说明 |
| **SNMP** | 网管系统采集状态 | 161 / 162 | ⚠️ 用的 v2c，community 明文，且开放了整棵 MIB 树 |
| **NTP** | 时间同步 | 123 | ✅ 已配置，但单点且无认证 |
| **AAA** | 认证、授权、计费 | - | ✅ 本地用户认证，密码不可逆加密 |
| **FTP** | 传配置/升级包 | 20/21 | ⚠️ jxtrq 账号开放了 ftp，明文传输 |

> ⚠️ **易错提示：看到 `http secure-server enable` 不要直接打勾说"HTTPS 已安全开启"**
>
> 这个判断至少漏了三层：
>
> **① TLS 版本和套件已经过时**
> ```huawei
> ssl policy default_policy type server
>  version tls1.0 tls1.1                        ← 都已被 RFC 8996 正式废弃
>  ciphersuite rsa_aes_128_cbc_sha              ← CBC 模式 + RSA 密钥交换，无前向保密
> ```
> 现代浏览器会**直接拒绝连接**这类站点。合规标准（PCI-DSS 等）也明令禁止。
>
> **② 服务开了，但可能根本访问不到**
> ```huawei
> http server permit interface GigabitEthernet0/0/9
> ```
> 这行的意思是：HTTP/HTTPS 服务**只允许从 G0/0/9 这个接口访问**。
> 而 G0/0/9 在这份配置里**没有配 IP 地址**，等于这个口不通。
> 结果就是——**Web 管理从任何地方都连不上**。
>
> 这有两种解读，**配置本身无法区分**：
> - (a) 有意的加固：关掉 Web 管理，只留命令行 → 做得对
> - (b) 配置遗漏：想开 Web 管理但忘了给 G0/0/9 配 IP → Web 管理是坏的
>
> 从整体风格（SSH、AAA 都配了）看，倾向于 (a)。
>
> **③ 真正的判断标准**
> 安全检查不能只看"服务有没有 enable"，要看：
> **是否可达 + 用什么协议版本 + 谁能访问 + 认证强度如何**。
> 四个维度全过才算安全。

### 为什么 NTP 对安全特别重要

日志、证书有效期、计费、故障排查全部依赖时间。**时间不对 = 日志没有取证价值**。出了安全事件，几台设备日志对不上时间戳，等于白记。

```
ntp-service source-interface LoopBack0
ntp-service unicast-server 192.20.27.30
```

用 Loopback 当源（稳定），从 LAN A 里的 `192.20.27.30` 同步时间。

### AAA 是什么

- **Authentication（认证）**：你是谁？
- **Authorization（授权）**：你能干什么？
- **Accounting（计费/审计）**：你干了什么？

```
aaa
 local-user admin password irreversible-cipher $1a$...
 local-user admin privilege level 15          ← 授权：15 级
 local-user admin service-type telnet http    ← 只允许 telnet 和 http 登录
 local-user jxtrq privilege level 3           ← 授权：3 级（**不要以为这是只读**，见下方）
 local-user jxtrq service-type terminal ssh ftp
```

**华为命令/用户级别（0-15）**：

| 命令级别 | 名称 | 典型命令 | 用户级别达到此值才能执行 |
|---|---|---|---|
| 0 | 参观级 | `ping`、`tracert`、`telnet`、`display version` | ≥0 |
| 1 | 监控级 | 大部分 `display`、`display current-configuration` | ≥1 |
| 2 | 配置级 | 业务配置：接口 IP、路由协议、ACL | ≥2 |
| **3** | **管理级** | **文件系统、FTP/TFTP 下载、`reboot`、用户管理、改命令级别** | **≥3** |
| 4-15 | - | 保留；设备可用 `command-privilege` 把个别命令提到更高级别 | ≥该值 |

> ⚠️ **易错提示：不要说"level 3 = 只读"**
>
> 这是本文档原稿的一个错误，也是很多人对华为权限体系的误解。三点必须说清：
>
> **① 绝大多数命令的最高级别就是 3**
> 华为命令默认只分 0~3 级。判断规则是简单的比较：**用户级别 ≥ 命令级别 → 允许执行**。
> 所以一个 level 3 的用户，能执行级别 ≤3 的**全部命令**——包括配置文件管理、
> FTP 下载配置、`reboot` 重启设备、甚至 `local-user` 改其他用户。**这已经是很高的权限了。**
>
> 想要真正的"只读"，应该设为 **level 1**（只能 display，不能进 system-view 改配置）。
>
> **② 命令级别是可以被重新分配的**
> ```huawei
> command-privilege level 15 view shell reboot      ← 把 reboot 提到 15 级
> command-privilege level 1 view shell display      ← 让 1 级用户也能 display
> ```
> 设备管理员可以逐条调整，所以**不同设备上同一个级别的实际能力可能完全不同**。
>
> **③ 最终权限是多个因素叠加的结果**
> 一个用户实际能干什么，至少要看四处：
> ```
> ① AAA 里的 local-user privilege level（本例：admin=15, jxtrq=3）
> ② 用户接口下的 user privilege level（本例：vty 0 设了 15，会覆盖/提升）
> ③ 命令自身的级别（默认 0-3，或已被 command-privilege 改过）
> ④ 认证/授权方式（是否走了 domain 下的 authentication-scheme / authorization-scheme）
> ```
> 本例中 `user-interface vty 0` 还额外设了 `user privilege level 15` —— 即便某个账号
> 只有 3 级，从 vty 0 登录也可能被抬到 15 级。**这就是为什么不能只看一行配置下结论。**
>
> **正确表述**：jxtrq 是 level 3 用户，属于"管理级"，具备相当高的操作权限；
> 它比 admin（level 15）低，但**绝不是只读账号**。

密码存储方式：
- `cipher`：可逆加密（设备能还原，用于某些需要明文密码的协议）
- **`irreversible-cipher`：不可逆加密**（哈希，安全性更高）✅ 配置里 admin 和 jxtrq 都用了这个

### VTY / Console：登录通道

```
user-interface con 0              ← Console 口（接串口线，物理接触）
 authentication-mode password     ← 只要密码，不要用户名
user-interface vty 0              ← 第 1 个远程登录通道
 authentication-mode aaa          ← 用 AAA 认证（要用户名+密码）
 user privilege level 15           ← 一登录就是 15 级
user-interface vty 1 4            ← 第 2~5 个远程登录通道
 authentication-mode aaa
```

`vty 0 4` 表示 vty 0 到 vty 4 共 5 个通道 = **最多 5 个人同时远程登录**。

⚠️ **这份配置的安全问题**：`user-interface vty 0` 直接给了 privilege level 15，且**没有用 ACL 限制哪些 IP 能登录**。任何人只要拿到密码就能从全网任意位置登录并拿到最高权限。详见精读文档的安全审计章节。
